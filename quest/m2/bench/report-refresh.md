# [S] Benchmark report refresh, before rind 0.4

## Goal

`BENCHMARKS.md`, and with it the README's heatmap, is regenerated on all six hosts before rind 0.4 is released, and every new gap is triaged as the Plan sets out.

## Plan

Decided with the maintainer on 2026-11-03: rerun the report regularly. On 2026-11-09: ✅ once before each minor release (rejected: at the end of each milestone, as first decided, since m2 holds outside waits that may never clear; leaving it there).

- Recurring, with nothing gating this run: it is ready now, and four `benchmarks/gaps.toml` entries wait on it. [rind 0.4's release](/quest/m2/api/release-0.4.md) requires it. The PR that finishes it deletes this file with `quest rm`, which clears that link. The next run is created with the next minor release's quest, at this path, required by that quest, with this Plan carried forward from git history; the release quest's Plan says so too.
- Run `admin/bench-report`, review the diff for regressions, and triage gaps above about 10% into speed quests or recorded reasons in `benchmarks/gaps.toml`, which `render` requires. The nightly's `gate` job owns regressions on the CPU tiers and this run owns the report: the hosts, the libraries the nightly leaves out, and the README's claims.
- Settled with the maintainer when the report was planned (2026-11-03), so don't reopen them: the hosts `nixos`, `desktop`, `nixos2`, and `kixtop`, each on its native path, to which `admin/bench-report`'s `HOSTS` adds the VPSes `ovh-iad` and `ovh-sea`; the libraries rind, aws-lc-rs, ring, RustCrypto with dalek, graviola, libcrux, and OpenSSL; a ✓ only where a published proof covers the whole computation that library runs on that host, padding included. A gap needs a quest that closes it when the operation is common or the gap is large, and otherwise gets a recorded reason.
- The bar, settled for the m2 speed epic (maintainer, 2026-11-01): the fastest permissively licensed source usable from Rust (aws-lc-rs, ring, RustCrypto, libcrux, graviola, BoringSSL, s2n-bignum, ...), on every x86_64, aarch64, and armv7 tier the nightly bench forces, at symmetric sizes 32 B, 1200 B, 1350 B, and 16 KB (plus 64 B and 8 KB for hashes, and 128 B, 256 B, and 512 B for AEADs, added on 2026-11-09 for the AEAD dispatch thresholds). Copyleft sources don't count.
- Source rule, decided with the maintainer on 2026-11-09, replacing "verified code within about 10% stays": run the fastest permissively licensed source; take a formally verified one only where it measures as fast at every size; otherwise run the fastest and plan its proof ✅ (rejected: verified code within about 10% on cold tiers only, or everywhere, as AGENTS.md said). The 1.10× threshold for a `gaps.toml` decision is separate and stays.
- So this run triages every cell where rind keeps verified code that measures slower than the fastest source, however small the margin. Each becomes a speed quest that switches the source plus a proof quest for what then runs, or a recorded reason. The ones the 2026-11-09 speed audit knew:
  - P-256 verification without ADX, on s2n-bignum's `_alt` routines rather than aws-lc's `ecp_nistz256`: 1.14× in `benchmarks/gaps.toml`, 1.07× in [run 42526977036](https://github.com/kixel-ai/rind/actions/runs/42526977036).
  - Ed25519 verification with ADX, on s2n-bignum's routines: 1.09× RustCrypto's time on `nixos` and 1.06× on `nixos2` in `benchmarks/data`.
  - ChaCha20 on HACL*'s rounds, as ALGORITHMS.md records: for one block with AVX2, where Graviola's kernels measured 1.05 to 1.3× faster on Coffee Lake, Arrow Lake, and Zen 3 and slower on Zen 5; and up to 128 bytes without AVX2, at 0.92 to 1.07 of aws-lc's integer routine's time.
  - The portable backend's HACL* hashes: SHA-512 at 1.20 to 1.27× aws-lc's C on that run's portable row, and SHA-256, which lost to Graviola's by 28 to 30% on armv7 (`benchmarks/armv7-sha256.md`) and is unmeasured against it on a 64-bit target.
- Triage, settled when the m2 speed epic closed (maintainer, 2026-11-09): this PR records each gap that needs a quest as a suggested follow-up in its body, which `/quest-merge` plans into the milestone the maintainer picks; the `gaps.toml` entry names that quest once it exists, and gives a reason until then.
- The every-logical-CPU handshake rows are the first this run fills. Each host's text gives rind-rustls's throughput on all its logical CPUs over its one-thread rate; no check fails on it, so read it, and open a quest for a host where it falls from the last run or trails aws-lc-rs's scaling. Those rows measure the host's other load as much as rind, so rerun a host whose result is marked noisy before reading them.
- Recheck the README's opening against the new results: its claims, such as which operations trail aws-lc-rs and ring, must still hold.
- The first report's `nixos2` gaps in Ed25519 verify (1.13 against RustCrypto) and ML-KEM-768 encapsulation (1.23 against graviola) come from its older run. Recheck them with a fresh `nixos2` run, and plan a speed quest for either that still holds.
- Every report so far timed rind's Ed25519 verify with a key parse, about 4 µs, that RustCrypto's and aws-lc-rs's rows skip. [kixel-ai/rind#464](https://github.com/kixel-ai/rind/pull/464) parses it once, so this run's Ed25519 verify rows for rind, graviola, OpenSSL, aws-lc-rs, and RustCrypto are the first that time the same work: drop any `gaps.toml` entry they close. ring's and libcrux's APIs take raw key bytes, so their rows still include the parse: rind beating them does not show its verify alone is faster, and a `gaps.toml` reason that rests on those rows says so.
- `kixtop` (Apple M4) joined the report in [kixel-ai/rind#435](https://github.com/kixel-ai/rind/pull/435) (maintainer, 2026-11-07); this run measures it like the other hosts.
